# Architecture

## One repository, two surfaces

```text
                 contributors (10-15)                          readers (millions)
                         │                                             │
                         │ HTTPS + bearer token                        │ HTTPS GET
                         ▼                                             ▼
   ┌──────────────────────────────────────┐        ┌──────────────────────────────────┐
   │ nginx  /v1/manage/*  → 127.0.0.1:8787 │        │ nginx  /v1/*  → static files     │
   └──────────────┬───────────────────────┘        │  root = www/current (symlink)    │
                  ▼                                 └──────────────▲───────────────────┘
   ┌──────────────────────────────────────┐                        │ atomic symlink switch
   │ management service (Tornado)         │                        │
   │  validate → data/ → build v1/ →      │──── publish release ───┘
   │  git commit (author = contributor) → │
   │  git push origin main                │
   └──────────────┬───────────────────────┘
                  ▼
        github.com/getbible/bookmarks  ◄──── pull requests, CI (build --check)
                  │
                  ▼  deploy/deploy.sh (systemd timer): fetch, verify, publish
```

The read side has no runtime. nginx serves the committed `v1/` tree from an
immutable release directory with precompressed `.gz` siblings, file ETags and
long `stale-while-revalidate` caching. The write side is a single small
process that turns each authenticated request into one validated git commit.

## Canonical sources (`data/`)

| File | Content |
|---|---|
| `topics.json` | `schema_version`, `catalog_version`, and the active topics: `id`, English `name`, lowercase hex `color`, sorted `aliases`, `default` flag |
| `retired-topics.json` | permanent tombstones: `id`, last `name`, `retired_in` catalogue version, optional `reason` |
| `links/<topic>.json` | strictly ascending, duplicate-free `[book, chapter, verse]` triples for one topic |
| `locales/<locale>.json` | translated topic names for one locale, optional English `name` of the language |

The sources are the only thing humans or the service edit. Everything under
`v1/` is derived and regenerated by `getbible-bookmarks build`; CI fails when
the committed tree is not byte-identical to a fresh build.

## Determinism and versioning

- JSON is rendered by one writer (`getbible_bookmarks.jsonfmt`): two-space
  indentation, insertion-ordered keys, scalar arrays on one line, UTF-8 without
  escaping, trailing newline. The same sources always yield the same bytes.
- `catalog_version` is a positive integer in `data/topics.json` that increases
  by exactly one on every published change. The service bumps it; pull requests
  must bump it (CI enforces this when `data/` changes).
- `checksum` is the SHA-256 of `v1/catalog.json`. `index.json`, `topics.json`,
  `locales.json`, `retired.json`, `all.json` and `checksums.json` carry both
  `catalog_version` and `checksum`, so a client holding any one of them knows
  exactly which catalogue it has. Leaf documents (`topics/<id>.json`,
  `verses/...`, `locales/<locale>.json`) carry only their data and therefore keep
  their ETag until their own content changes.
- `schema_version` is `1` everywhere. Incompatible shape changes get a new
  `schema_version` and a new path prefix (`v2/`); the `v1/` tree keeps being
  generated for as long as consumers need it.

## Invariants

Enforced by `getbible_bookmarks.model` and identical to the rules the
getbible/robot contribution pipeline applies, so its exports import unchanged:

| Rule | Detail |
|---|---|
| Topic id | lowercase slug `[a-z0-9]+(-[a-z0-9]+)*`, at most 80 characters, permanent |
| English name | `[A-Za-z0-9][A-Za-z0-9 &'():?-]*[A-Za-z0-9)]`, at most 80 characters |
| Uniqueness | names and aliases are unique across all active topics, case and whitespace insensitive |
| Rename | the previous wording becomes an alias automatically so stored mappings keep resolving |
| Colour | `#rrggbb`, lowercase |
| Aliases | at most 20, sorted, never equal to the name |
| Verse coordinate | book 1..66, chapter within the fixed Protestant chapter counts, verse 1..2000 |
| Retirement | removes the topic, its links and translations; the id is tombstoned and can never be reused |
| Locale code | lowercase BCP 47 style tag (`fr`, `zh-hant`); `en` is derived from the topics and cannot be edited as a locale |
| Translated name | 1..120 characters, no control characters, NFC normalised |
| Limits | 1,000 topics, 100,000 verse links, 500 locales, 10,000 coordinates per request |

## Security boundaries

- The static tree is public, immutable per release, world-readable, and
  contains no personal data: no contributor identity, timestamps or notes.
  Contributor identity appears only in git author metadata.
- The management API listens on loopback only. nginx terminates TLS, rate
  limits, bounds body size and forwards `X-Real-IP` for per-address limits on
  failed authentication.
- Tokens are 256-bit random secrets with a `gbb_` prefix. The registry stores
  SHA-256 digests only, in a mode-0600 file outside the repository; comparison
  is constant time across all entries. Issuance, rotation and revocation are
  CLI operations on the host, never HTTP operations.
- Two roles: `contributor` (verse links, translations, bundles) and
  `maintainer` (topic lifecycle, locale deletion, sync). Role checks happen
  before any state is touched.
- Every request body is parsed strictly: JSON objects only, unknown fields
  rejected, bounded sizes, canonical validation before any write.
- Mutations are serialized by a process lock and a `flock` shared with
  `deploy/deploy.sh`, so the checkout can never be written concurrently.
- The service refuses to act on a dirty checkout or the wrong branch, rebases
  unpushed local commits onto the remote before committing, and reports a
  divergent history instead of guessing.
- systemd hardening (`ProtectSystem=strict`, read-write only on the checkout
  and release root, no capabilities, syscall filter) limits what a compromised
  process could reach; the deploy key is scoped to this repository.

## Failure modes

| Situation | Behaviour |
|---|---|
| GitHub unreachable during a write | the commit is made locally and served; the push is retried every minute and by the next mutation; `status` reports `push_pending` |
| Push rejected because `main` moved | the service fetches and rebases its unpushed commits on the next attempt; a textual conflict stops with HTTP 503 `repository_diverged` for an operator |
| Invalid request | HTTP 400/404/410/422 with a precise message; nothing is written |
| Two contributors edit simultaneously | requests are serialized; the optional `expected_catalog_version` field turns a lost update into HTTP 409 |
| Service down | the static API keeps serving the last release; writers get 502 from nginx |
| Bad release | switch the `current` symlink back to the previous release directory, or `git revert` and run `deploy/deploy.sh` |
